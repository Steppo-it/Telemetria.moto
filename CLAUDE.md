# Telemetria Moto — CLAUDE.md

Documento di contesto per Claude Code (o chiunque riprenda il progetto in VS Code). Contiene tutto quello che serve per capire cosa è stato costruito, come, e perché, senza dover rileggere l'intera cronologia della chat originale.

## Cos'è

Una PWA (single-page, single-file) per iPhone che, montata sul cruscotto/manubrio di una moto, mostra e registra in tempo reale: angolo di piega, beccheggio, accelerazione/frenata, velocità GPS, un punteggio di guida calcolato, e una mappa di navigazione con percorso evidenziato. Pensata per essere usata **in marcia**, con telefono fisso su supporto, schermo sempre visibile, landscape only.

L'interfaccia si presenta ("brand") come **TELAMETRIA** — "By TelaStampiamo" in piccolo accanto — nella topbar dell'app (`.brand`). Il nome del progetto/repo resta "Telemetria Moto" (da cui il titolo di questo file e il nome cartella); il rebrand riguarda solo la UI mostrata all'utente, introdotto nel redesign layout v2 (vedi sotto).

Non è un progetto con build system, bundler o package manager: è **un solo file HTML** (`index.html`) con CSS e JS inline, pensato per essere servito staticamente via GitHub Pages. Nessuna dipendenza da installare lato sviluppo.

## Stack tecnico

- **Nessun framework** — HTML/CSS/JS vanilla, tutto in un file.
- **Google Maps JavaScript API + Directions API** — mappa e calcolo percorso (richiede una API key dell'utente, vedi sotto).
- **Geolocation API** (`navigator.geolocation.watchPosition`) — posizione, velocità, direzione (heading).
- **DeviceOrientationEvent / DeviceMotionEvent** — piega, beccheggio, accelerazione (richiedono permesso esplicito su iOS 13+ via `requestPermission()`, deve partire da un tap diretto dell'utente).
- **localStorage** — persistenza di tre preferenze utente: tema chiaro/scuro (`moto_theme`, `dark`/`light`, impostato dal toggle **Tema** nel pannello comandi unico — vedi sotto — e riletto anche prima del rendering, in un piccolo `<script>` in `<head>`, per evitare un flash del tema sbagliato), voce navigatore attiva/disattiva (`moto_voice`, vedi sezione Mappa e navigazione) e disposizione delle 3 card grandi (`moto_card_layout`, sceso da 4 a 3 in questo round — vedi sezione Layout). Le vecchie preferenze `moto_map_pct` (dimensione mappa via drag) e `moto_mini_layout` (scelta dei mini-tile Sessione/Distanza/Velocità/Punteggio) **non esistono più**: il ridimensionamento mappa è stato rimosso deliberatamente nel redesign layout v2, e i mini-tile personalizzabili sono stati a loro volta sostituiti dai pulsanti rapidi **Avvio/Menù/Calibra** (vedi sezione Layout). Nota: questo NON è un artifact di Claude.ai, gira su una pagina servita esternamente via GitHub Pages, quindi `localStorage` è pienamente supportato (a differenza degli artifact in claude.ai dove è vietato).
- **Font esterni**: Google Fonts (Orbitron per i numeri grandi/display, JetBrains Mono per i dati, Inter per testo secondario).
- **Hosting**: GitHub Pages (repo pubblico — Pages su repo privati richiede un piano a pagamento).

## Struttura del file

`index.html` (~1350 righe) è organizzato in tre blocchi:
1. `<style>` — tutte le variabili CSS in `:root` (colori, font) + layout
2. `<body>` — markup statico di tutti i pannelli/card/popover
3. `<script>` — un'unica IIFE con tutta la logica, più il tag `<script>` di Google Maps in fondo alla pagina (con `defer`, carica dopo lo script principale ma prima che l'utente possa interagire)

Non ci sono altri file JS/CSS esterni al progetto oltre a Leaflet (rimosso) → ora solo Google Maps via CDN ufficiale Google.

## Setup per sviluppo locale

Non serve build. Per sviluppare:
1. Apri `index.html` in un editor
2. Per testare nel browser desktop: un semplice server statico basta (`python3 -m http.server` nella cartella, poi apri `localhost:8000`). **Attenzione**: sensori (DeviceOrientation/Motion) e spesso anche GPS ad alta precisione richiedono un contesto reale su dispositivo mobile — il desktop è utile solo per verificare che non ci siano errori JS e che la mappa carichi.
3. Per testare su iPhone davvero: serve HTTPS (Safari blocca Geolocation su `http://` e su `file://`). In sviluppo, il modo più comodo resta pushare su GitHub Pages e aprire l'URL pubblico da Safari — non da webview integrate in altre app (bug noto, vedi sotto).

## Setup chiave Google Maps (obbligatorio)

La mappa **non funziona** senza una chiave valida. Nel file, in fondo, c'è:
```html
<script src="https://maps.googleapis.com/maps/api/js?key=YOUR_GOOGLE_MAPS_API_KEY&v=weekly&libraries=places" defer></script>
```
Va sostituito `YOUR_GOOGLE_MAPS_API_KEY` con una chiave reale creata su [Google Cloud Console](https://console.cloud.google.com/), con **Maps JavaScript API** e **Directions API** abilitate sul progetto, **billing attivo** (richiesto anche per restare nel piano gratuito), e idealmente con restrizione **HTTP referrer** limitata al dominio GitHub Pages del progetto (`https://<utente>.github.io/*`) — la chiave finisce in un repo pubblico quindi la restrizione è l'unica vera protezione. Abilita anche la **Places API** (⚠️ non "Places API (New)": sono due prodotti Google distinti — il widget usato nel codice, `google.maps.places.Autocomplete`, richiede la Places API "legacy". Abilitare per sbaglio solo quella "(New)" causa un `ApiTargetBlockedMapError` in console e il popup "Questa pagina non carica correttamente Google Maps" — già successo una volta, vedi HANDOFF.md) sullo stesso progetto/chiave se vuoi l'autocomplete indirizzi nel navigatore (vedi sotto) — senza, i campi indirizzo degradano a testo libero senza errori.

## Deploy

GitHub Pages, repo **pubblico** (Pages su repo privati richiede piano Team/Enterprise). Settings → Pages → Deploy from a branch → `main` → `/ (root)`. `index.html` deve stare nella root del repo (non in una sottocartella) perché GitHub Pages lo serve automaticamente come pagina principale.

## Come si usa (flusso utente reale)

1. Monta il telefono su supporto, landscape. **Tutti i controlli sono raggruppati in alto** (mini-riga Avvio/Menù/Calibra a sinistra, pulsanti mappa recenter/segnalino/naviga in alto sulla mappa) — scelta deliberata di questo round: sul dispositivo reale dell'utente la parte bassa dello schermo si è rivelata scomoda da raggiungere una volta montato sul cupolino, vedi sezione Layout.
2. Apri l'URL GitHub Pages **direttamente in Safari** (non dentro webview di altre app — vedi Problemi noti). **Mappa e posizione compaiono da sole all'apertura** (richiesta il permesso GPS subito, non serve più premere Avvia solo per vederle — vedi sezione Mappa).
3. Tocca **Calibra** (mini-riga in alto a sinistra) a moto ferma **con il motore acceso**: raccoglie ~1.5s di rumore reale dei sensori (vibrazioni motore comprese) per calibrare le deadzone su misura, poi azzera l'offset di piega/beccheggio e resetta la stima di gravità dell'accelerometro — vedi sezione "Calibrazione".
4. Tocca **Avvio** (mini-riga in alto a sinistra, o **Avvia** nel pannello comandi — stesso pulsante, stesso stato): richiede i permessi sensori (se non già concessi — il GPS è già attivo dal passo 2), inizia a tracciare e a loggare i dati.
5. Guida. Le tre card grandi (piega con icona moto, beccheggio, trasferimento carico) nelle due colonne laterali sono pensate per essere lette a colpo d'occhio anche a velocità sostenuta.
6. Facoltativo: tocca l'icona 🧭 in alto sulla mappa per impostare una destinazione — disegna il percorso come linea evidenziata e attiva la barra navigatore sopra la mappa (manovra, distanza, ETA). Durante la registrazione, tocca 🚩 (segnalino, in alto sulla mappa) per segnare l'istante e la posizione correnti nel CSV — utile per poi ritrovare un punto notato in marcia (es. "ho frenato troppo qui") e confrontarne i dati sensore.
7. A fine giro: apri il pannello comandi (Menù), tocca **Ferma** (richiede conferma via `confirm()` nativo, per evitare stop accidentali), poi **CSV** per esportare i dati registrati (scarica un file via Safari, l'utente lo recupera dall'app File).

## Funzionalità implementate

### Sensori e calcolo dati

- **Piega (roll) e beccheggio (pitch)**: NON più letti da `deviceorientation` (`beta`/`gamma`, limite noto: sono angoli di Eulero, soggetti a gimbal lock/salti discontinui quando `beta` si avvicina a ±90°). Calcolati entrambi in `handleMotion()`, rispettivamente da `computeLeanFromGravity()`/`computePitchFromGravity()`, a partire dallo stesso vettore di gravità grezzo e istantaneo (non dal filtrato `gEst`, vedi sotto), compensato per l'orientamento schermo (`compensateAccelXY()`, `screen.orientation.angle`) — necessario perché il telefono può essere montato sia verticale che orizzontale e i valori grezzi del sensore non seguono automaticamente la rotazione dell'interfaccia. `handleOrientation()` (l'handler di `deviceorientation`) si occupa ormai solo di catturare l'heading bussola (`webkitCompassHeading`) — la funzione `compensateOrientation()`, usata in passato per compensare beta/gamma, è stata rimossa perché non più referenziata da nulla.
  - **Storia (due round di correzione)**: la piega veniva prima calcolata da `gamma` (tramite `compensateOrientation()`, ora rimossa); il beccheggio era già stato spostato su `computePitchFromGravity()` in una fase precedente proprio per il gimbal lock di `beta`. **Round 1**: sollevando il telefono oltre ~30° di beccheggio, la piega letta da `gamma` "impazziva" fino a ~170° — è la coppia `beta`/`gamma` nel suo insieme a degenerare quando `beta` si avvicina ai poli. Prima correzione: `computeLeanFromGravity()` con `atan2(comp.x, gz)` (due argomenti con segno, stesso principio del beccheggio). **Round 2 (lo stesso bug si è ripresentato identico dopo la prima correzione)**: quella prima versione risolveva il gimbal lock di `beta`/`gamma` ma introduceva un problema equivalente per un'altra via — con un supporto che monta il telefono già molto inclinato di suo (es. su un cupolino, ~60° dalla orizzontale), la componente Z grezza del sensore a riposo è già piccola, e bastano ~30° di beccheggio *reale* aggiuntivo per farla passare per zero: `atan2(x,z)` diventa instabile proprio in quella zona, perché sia x che z si avvicinano contemporaneamente a zero. **Correzione finale**: `computeLeanFromGravity()` usa `Math.sqrt(comp.y² + gz²)` come secondo argomento invece del solo `gz` — quel denominatore resta vicino alla norma piena di gravità (~9.8) qualunque sia il beccheggio, perché il beccheggio sposta la gravità *dentro* il piano Y-Z senza farla uscire. Come contropartita la piega torna limitata a ±90° (accettabile: una moto non piega oltre l'orizzontale in condizioni normali, a differenza del beccheggio durante un'impennata, che invece necessita del range esteso). **Verificato numericamente e in simulazione browser** riproducendo lo scenario esatto segnalato (montaggio di base a 60°, beccheggio reale crescente, piega reale costante a 15°): la versione Round 1 salta da 15° a -165° esattamente al superamento dei 30° aggiuntivi (bug riprodotto fedelmente); la versione finale resta in un intervallo ragionevole (0-7° nel caso peggiore di composizione dei due movimenti) per l'intero beccheggio testato, mai un salto.
  - **Limite residuo noto e accettato**: la formula finale non è perfettamente indipendente dal beccheggio in caso di piega e beccheggio estremi *simultanei* (l'esatta accuratezza dipende dall'ordine/composizione reale dei due movimenti, che varia caso per caso) — ma non produce mai più salti bruschi tipo gimbal-lock, solo una deriva contenuta. Limite intrinseco di qualunque coppia di angoli ricavata dal solo vettore di gravità (servirebbe un terzo riferimento, es. bussola/giroscopio, per un'indipendenza perfetta), non specifico di questa formula.
  - **Round 3 — rete di sicurezza indipendente dalla causa, e sospetto di cache**: dopo il Round 2, l'utente ha segnalato lo stesso sintomo altre due volte (piega a ~170°, poi a ~180°, sempre superati i ~30° di beccheggio) — testato su strada, non in simulazione. Punto chiave: la formula del Round 2 (`atan2(comp.x, sqrt(comp.y²+gz²))`, secondo argomento sempre ≥0) è **matematicamente limitata all'intervallo ±90°** — non può *per costruzione* restituire 170° o 180°, qualunque sia l'input. Un salto a quei valori è quindi la firma della formula del Round 1 (`atan2(x,z)`, range pieno ±180°) o di quella ancora precedente basata su `gamma`, non del codice attualmente in `main`. Sospetto forte (non confermato): l'utente sta testando una **pagina in cache** (iOS Safari cachea aggressivamente, specie se l'app è aggiunta alla schermata Home) e non la build più recente. Per questo:
    1. Aggiunto un marcatore `BUILD_VERSION` (costante in cima alla IIFE dello script) visibile in Impostazioni → riga "Versione" in fondo al pannello — permette di verificare a colpo d'occhio se il telefono sta effettivamente caricando l'ultima build prima di dare per buono/rotto un fix.
    2. Aggiunta comunque, indipendentemente dalla causa, una **rete di sicurezza difensiva**: `clampImplausibleLeanJump(newVal, now)`, con `MAX_LEAN_RATE_DEG_S = 300` — se un singolo campione di `computeLeanFromGravity()` cambierebbe la piega di più di 300°/secondo rispetto all'ultimo valore accettato, il salto viene limitato a quel tasso massimo invece di essere applicato di colpo (non è un semplice "ignora il campione": se l'input resta anomalo su più campioni consecutivi, la lettura converge gradualmente verso il nuovo valore invece di restare bloccata per sempre). 300°/s è ampiamente superiore a qualunque piega reale in marcia, anche aggressiva — pensato per non interferire mai con letture legittime. Verificato in browser: un salto forzato a ~170-180° viene soppresso all'istante (es. 12°→1°) e converge in ~20 campioni successivi (30ms l'uno) verso il nuovo valore reale, se questo persiste.
    - **Non risolto**: la causa ultima del sintomo riportato dopo il Round 2 resta da confermare — se il marcatore versione conferma che l'utente vede l'ultima build e il salto si ripresenta comunque, il problema è reale e va riaperto (in tal caso, oltre alla piega, controllare `angle`/`screen.orientation.angle` sul dispositivo reale in landscape: la logica è stata verificata solo con `angle=0`).
- **Accelerazione/frenata**: da `devicemotion.accelerationIncludingGravity`, con **filtro passa-basso per stimare e sottrarre la componente di gravità** (tecnica standard tipo "gravity sensor" software, vedi `gEst` e `G_ALPHA = 0.85` nel codice), poi compensata per orientamento schermo (`compensateAccelXY()`). L'asse Y del dispositivo (dopo compensazione) è trattato come longitudinale (avanti/freno, `fwdG`), X come laterale (`latG`), Z come verticale (`vertG`).
- **Indice "Assetto"/comfort**: RMS mobile dell'accelerazione verticale su una finestra di 40 campioni (`vertBuf`/`VERT_BUF_LEN`), mappato 0–100. **Stima**, non una misura reale di smorzamento sospensioni (richiederebbe un sensore sulla ruota). Calcolato internamente per il punteggio ma non mostrato come tile a sé (rimosso su richiesta utente prima del redesign v2, ancora così dopo).
- **Punteggio di guida**: tre sotto-punteggi con media mobile esponenziale (`SCORE_ALPHA = 0.03`): fluidità accelerazione/frenata (40%), pulizia in piega — basata sulla velocità angolare del roll (35%), compostezza/comfort verticale (25%). Calcolato ad ogni campione `devicemotion` e loggato nel CSV (colonna `score`), ma **non ha più una rappresentazione a schermo**: era mostrabile solo come mini-tile opzionale (rimosso, vedi sezione Layout).
- **Calibrazione** (`runCalibration()`, chiamata sia da `#calibBtn` nel pannello comandi sia da `#miniCalibBtn` nella mini-riga in alto — stesso gestore condiviso `handleCalibClick()`): due fasi.
  1. **Calibrazione rumore** (nuova in questo round): raccoglie ~1.5s (`CALIB_SAMPLE_MS`) di campioni grezzi via `collectNoiseSamples()` — un listener `devicemotion` temporaneo, aggiunto DOPO quello di `handleMotion()` (quindi vede sempre `lastRawRoll`/`lastRawPitch`/`linear` già aggiornati per il campione corrente) e rimosso a fine raccolta. Calcola la deviazione standard (`stdDev()`) di piega/beccheggio/G raccolti a moto ferma — **vibrazioni motore comprese, se il motore è acceso durante la calibrazione** (richiesto nel flusso d'uso, vedi sopra) — e imposta `LEAN_DEADZONE_DEG`/`PITCH_DEADZONE_DEG`/`G_DEADZONE` (ora `let`, non più `const`) a 3 deviazioni standard, con margini min/max (0.5°–6° per gli angoli, 0.02g–0.15g per le G) per non azzerare la sensibilità né lasciarla troppo aggressiva se la sessione di calibrazione risulta insolitamente rumorosa. Mostra "Calibrazione in corso — tieni la moto ferma…" in `#logInfo` durante l'attesa. **Euristica non validata scientificamente** (3 deviazioni standard è una scelta ragionevole, non calcolata su dati reali) — da aggiustare se in marcia le deadzone risultanti sono troppo/poco aggressive.
  2. **Azzeramento offset** (comportamento preesistente, invariato): cattura gli ultimi valori grezzi (`lastRawRoll`, `lastRawPitch`, `lastRawAG`) e li usa come nuovo zero (`leanOffset`, `pitchOffset`, reset di `gEst`).

  I sensori restano "sempre attivi" una volta concessi i permessi — non sono legati al ciclo Avvia/Ferma, che controlla solo il logging (vedi `ensureSensors()` vs `start()`/`stop()`; il GPS invece è sempre attivo dall'apertura dell'app, vedi sezione Mappa). Questo comportamento aveva causato un bug reale sul vecchio timer di sessione mostrato a schermo (il valore continuava ad avanzare dopo **Ferma**) — non più rilevante da quando quella mini-tile è stata rimossa, vedi sezione Layout.

### Card grandi: piega, beccheggio, trasferimento carico

**Scese da 4 a 3** in questo round (richiesta esplicita: più spazio alla mappa, meno ai sensori). Le vecchie card separate **G Laterale** e **G Longitudinale** sono state sostituite da un'unica card **Trasferimento Carico** (`#cardLoad`) con un gauge a pallina invece di due barre numeriche — vedi sotto. Piega e beccheggio restano due card distinte, con una modifica solo alla card Piega (icona moto al posto della barra, vedi sotto).

- **Piega** (`#cardLean`): etichetta, numero grande, sottoetichetta SINISTRA/DESTRA, **icona moto rotante** (`#leanBikeIcon`, SVG inline) al posto della vecchia barra orizzontale — vedi sotto — poi riga massimi MAX SX/MAX DX.
- **Beccheggio** (`#cardPitch`): invariata nello stile — etichetta, numero, sottoetichetta SU/GIÙ, barra orizzontale centrata sullo zero (`.stat-bar-track`/`.stat-bar-fill`, riempita da `setBarFill()`), tacche, riga massimi UP/DOWN.
- **Trasferimento Carico** (`#cardLoad`): etichetta, gauge a pallina in una croce (`.load-gauge`/`#loadBall`) — vedi sotto — riga massimi TOP LONG/TOP LAT.

Tutte e 3 sono **monocromatiche** tranne la card Piega oltre soglia (ambra 25°/rossa 40° su numero e sottoetichetta — soglie arbitrarie, non calibrate su dati reali); il beccheggio e il carico non hanno soglie colore.

- **Massimi separati per lato/verso**: `maxLeanSx`/`maxLeanDx` (piega), `maxPitchUp`/`maxPitchDown` (beccheggio), `maxGLat`/`maxGLong` (carico, valore assoluto) — persistenti per tutta la sessione, si resettano a ogni **Avvia** (`start()`) o manualmente col pulsante **↺ Reset max** nel pannello comandi (richiede conferma via `confirm()` nativo).
- **Convenzione segno piega**: `rollDeg` negativo = destra (DX), positivo = sinistra (SX) — verso confermato su strada (era invertito nella prima versione del chevron, correzione persa e poi ripristinata, vedi commento in `updateLeanGauge()`). **Nota**: questa convenzione era validata sulla vecchia formula basata su `gamma`; la nuova `computeLeanFromGravity()` (vedi sopra) usa lo stesso segno per analogia ma non è stata ri-validata su strada in modo indipendente — se risultasse invertita, correzione di una riga (`comp.x` → `-comp.x` in `computeLeanFromGravity()`).
- **Convenzione segno beccheggio**: positivo = su (SU). Se risulta invertito su strada, invertire il segno in `computePitchFromGravity()` (cambia `Math.atan2(-comp.y, ...)` in `Math.atan2(comp.y, ...)`).
- **Calcolo beccheggio**: da `computePitchFromGravity()`, basato sul vettore di gravità **grezzo e istantaneo** (`rx`/`ry`/`rz` da `accelerationIncludingGravity`, letto in `handleMotion()`) — **mai** sul vettore filtrato `gEst`, che serve solo a stimare la gravità "a riposo" per il calcolo dell'accelerazione lineare. Usare `gEst` per il beccheggio causava un bug osservato su strada: durante un'impennata sostenuta il filtro passa-basso "insegue" la nuova inclinazione trattandola come nuova gravità, facendo scendere il beccheggio verso 0 (per poi ripartire da capo) anche se il telefono restava inclinato. `beta` di `deviceorientation` non viene usato per lo stesso motivo: è un angolo di Eulero e soffre di gimbal lock/salti discontinui (es. ~-350°) durante un'inclinazione estrema.
- **Formula beccheggio**: `Math.atan2(-comp.y, gz)` — due componenti **con segno**. Vedi sezione "Piega e beccheggio dal vettore di gravità" più sopra per la storia completa (3 round) e lo stato del bug residuo segnalato di nuovo dopo il Round 2 (in attesa di una registrazione CSV dell'utente per una diagnosi definitiva, invece di un altro tentativo "al buio" — vedi Round 3).
- **Icona moto rotante (card Piega)**: SVG inline (`<svg class="lean-bike-icon">`, ~60×60 viewBox: una linea "terreno" fissa + un gruppo `#leanBikeIcon` con ruota/telaio/manubrio stilizzati) che ruota via `style.transform = 'rotate(...)'` in `updateLeanGauge()`, `transform-origin` ancorato al punto di contatto ruota-terreno in fondo all'SVG, così la moto sembra "appoggiarsi" sul terreno invece di ruotare sul proprio centro. Sostituisce la vecchia barra orizzontale/tacche per questa sola card (più intuitiva di un numero su una barra lineare). **Segno**: `rotate(${-rollDeg}deg)` — invertito rispetto a `rollDeg` perché una rotazione CSS positiva è oraria (verso destra guardando lo schermo) mentre `rollDeg` negativo=DX; stessa inversione già usata (e persa una volta) dalla vecchia sagoma SVG pre-chevron.
- **Gauge Trasferimento Carico**: sostituisce le vecchie barre G Laterale/G Longitudinale con un singolo gauge circolare (`.load-gauge`, cerchio con crocevia) in cui una pallina (`#loadBall`) si sposta in base ai due assi G smussati (`gLatDisplay`/`gLongDisplay`, stessa EMA di prima, vedi sotto), calcolata in `updateLoadGauge(gLat, gLong)`. Scale ±1.5g laterale/±1.0g longitudinale (le stesse già usate dalle vecchie barre) — oltre quei valori la pallina resta ancorata al bordo invece di uscire dal cerchio. **Convenzioni** (nessuna nuova, solo una nuova resa visiva delle stesse): `fwdG` positivo=accelerazione/negativo=frenata (convenzione già confermata) → durante la frenata il trasferimento di carico va in avanti, quindi la pallina sale verso il tag FRENATA (in alto) quando `fwdG` è negativo; `gLat` negativo=DX/positivo=SX (stessa convenzione di `rollDeg`, **non validata indipendentemente su strada**, vedi nota sopra) → la pallina va verso il tag DX quando `gLat` è negativo. I vecchi TOP con verso (`DX`/`SX`, `FRENATA`/`ACCEL`) restano, ora nella riga massimi di questa card.
- **G laterale/longitudinale — valore smussato**: invariato, media mobile esponenziale separata per asse (`gLatDisplay`/`gLongDisplay`, `G_DISPLAY_ALPHA = 0.12`, aggiornata in `handleMotion()`) a partire da `latG`/`fwdG` grezzi — solo per la resa visiva (posizione della pallina), non per il punteggio guida che continua a usare i valori grezzi.
- **Deadzone (soglia minima di attivazione)**: `G_DEADZONE`, `LEAN_DEADZONE_DEG`, `PITCH_DEADZONE_DEG` — sotto questi valori piega/beccheggio/carico vengono mostrati come esattamente zero invece del rumore residuo dei sensori a moto ferma. Applicata solo alla resa a schermo (dentro `updateLeanGauge()`/`updatePitchGauge()`/`updateLoadGauge()`, prima di qualunque altro calcolo in quelle funzioni), mai ai valori grezzi usati per il punteggio guida. **Ora `let` invece di `const`** e ricalcolate dalla calibrazione rumore (vedi sezione "Calibrazione" sopra) — i valori iniziali (0.04g / 1.0° / 1.0°) restano solo il default finché non si esegue almeno una calibrazione in quella sessione.

### Mappa e navigazione

- **Google Maps JS API**, stile custom **nero puro / bianco puro** (`NIGHT_STYLE`/`DAY_STYLE` nel codice, selezionati da `mapStyleForTheme()`) coerente col sistema di temi chiaro/scuro del resto dell'HUD — cambia dal vivo (`gmap.setOptions({styles:...})`) quando si tocca il toggle **Tema** nel pannello comandi, senza ricaricare la pagina.
- Mappa **orientata a nord fisso** (non ruota con la direzione di marcia). Scelta deliberata e non un compromesso tecnico dimenticato: ruotare l'intera mappa via CSS (come si faceva con la versione precedente basata su Leaflet+OpenStreetMap) nasconderebbe/distorcerebbe il logo Google e il link ai Termini, che Google richiede restino sempre visibili per contratto. La direzione di marcia è invece indicata dalla **freccia arancione che ruota** sopra la mappa fissa.
- **Ridimensionamento mappa via drag: rimosso.** Nella v1 del layout esisteva una maniglia (`#resizeHandle`) trascinabile tra mappa e colonna HUD, che aggiornava una CSS custom property `--map-pct` (persistita in `moto_map_pct`) in tempo reale. Il redesign layout v2 lo ha eliminato **deliberatamente** — vincolo esplicito del piano di redesign, non una regressione: la mappa ora occupa sempre tutto lo spazio verticale disponibile nella colonna centrale (`.col-map { flex:1 1 auto }`), mentre le due colonne laterali hanno larghezza fissa (145px, `.col-side { flex:0 0 145px }` — ridotta da 168px in un round successivo, vedi sezione Layout). La custom property CSS `--map-pct` è rimasta dichiarata (inutilizzata, valore fisso `60%`) in `:root` — codice morto innocuo, nessun selettore CSS né riga JS la referenzia più.
- **Pan/zoom manuale + "follow mode"**: `gestureHandling: 'greedy'` (pan/pinch-zoom liberi, senza il suggerimento "usa due dita"). Un flag `mapFollowing` controlla se `updateMap()` ricentra/rizooma automaticamente sul GPS ad ogni fix: diventa `false` quando l'utente trascina la mappa (`dragstart`, scatta solo su interazione reale, mai su `setCenter`/`fitBounds` programmatici) o quando si imposta un percorso (per mostrarlo tutto via `fitBounds`, tappe comprese). Il pulsante 📍 (`#mapRecenterBtn`, appare solo quando `mapFollowing` è `false`) rimette `mapFollowing = true` e ricentra sull'ultima posizione nota. "Annulla percorso" ripristina il follow mode automaticamente.
- **Pulsanti flottanti sopra la mappa, tutti in alto**: 🧭 `#mapNavBtn` (apre il navigatore, in alto a destra — invariato), 📍 `#mapRecenterBtn` (in alto a sinistra — **spostato qui da in basso a destra** in questo round, stesso motivo di raggiungibilità della mini-riga, vedi sezione Layout) e 🚩 `#mapMarkerBtn` (segnalino, subito a destra del recenter — nuovo in questo round, vedi sezione "Segnalino" sotto). Nessuno di questi è stato toccato dal consolidamento della barra navigatore (vedi punto sotto), che riguarda solo le informazioni di avanzamento percorso.
- **`.map-empty` (overlay "In attesa di segnale GPS…") ha `pointer-events:none`**: prima di questo round, essendo l'ultimo figlio di `#colMap` con `z-index:402` (più alto dei pulsanti a 401) e `inset:0` (copre tutta l'area mappa), finché il GPS non risultava agganciato **intercettava silenziosamente i tap destinati ai pulsanti sopra la mappa**, rendendoli inutilizzabili proprio quando servirebbero di più (es. subito dopo l'apertura dell'app). Scoperto testando il nuovo pulsante segnalino. Fix minimo: `pointer-events:none` su `.map-empty`, che è solo testo informativo, mai un elemento con cui interagire.
- **GPS/mappa sempre attivi dall'apertura dell'app** (non più legati a `start()`/`startNavigation()`): `ensureGps()` viene chiamato una volta al caricamento della pagina, richiedendo subito il permesso di posizione (a differenza dei sensori di movimento, su iOS non serve un tap diretto dell'utente per questo). Prima di questo round, il GPS partiva solo premendo Avvia o impostando una destinazione, e si fermava (`stopGpsIfIdle()`, ora rimossa) quando nessuna delle due era attiva — comportamento cambiato su richiesta esplicita ("la mappa deve comparire subito"). Effetto collaterale accettato: consumo batteria/GPS continuo per tutta la sessione con l'app aperta, anche senza registrare.
- **Navigazione**: icona 🧭 apre un popover (`#navPanel`) con campo destinazione (`#destInput`, primo elemento del popover, prima delle tappe) + tappe intermedie opzionali (pulsante "+ Aggiungi tappa"), tutti con **autocomplete Google Places** (richiede la Places API abilitata sul progetto Google Cloud dell'utente, sulla stessa chiave — se non abilitata, i campi degradano a testo libero senza errori). Il percorso è disegnato con un effetto **glow**: due `DirectionsRenderer` sovrapposti sulla stessa mappa (`directionsRendererGlow` largo/trasparente sotto, `directionsRenderer` nitido sopra), entrambi aggiornati con lo stesso risultato.
- **`#navPanel` ancorato in alto, non in basso**: a differenza degli altri popover (`#controlPanel`, `#pickerPanel`, tutti `.popover-panel` con `bottom:12px` di default), `#navPanel` ha un override (`bottom:auto; top:12px`) che lo ancora in alto. Motivo: con la tastiera aperta per digitare l'indirizzo, un pannello ancorato in basso rischiava di finire coperto dalla tastiera stessa, portandosi dietro il campo e i suggerimenti Google Places — per lo stesso motivo `#destInput` è stato spostato come primo campo del popover (prima era dopo la lista tappe).
- **Istruzioni vocali**: Web Speech API (`speechSynthesis`, italiano), annuncio ad ogni manovra imminente (~150m prima, una sola volta per step) più un annuncio di conferma al click "Vai". Toggle **Voce navigatore** ora nel pannello comandi (`#voiceToggle`), persistito in `localStorage` (`moto_voice`). La logica di avanzamento (`navSteps`/`navStepIndex`/`updateNavProgress()`) appiattisce tutte le `legs[].steps[]` del risultato Directions in una sequenza unica, con un annuncio extra ("Tappa raggiunta") al passaggio tra una tappa e la successiva.
  - **Fix "la voce non funziona" (`primeSpeech()`)**: le policy anti-autoplay di iOS Safari ignorano in silenzio `speechSynthesis.speak()` se non chiamato **sincronamente dentro un vero tap dell'utente** — gli annunci turno-per-turno partono da `updateNavProgress()`, innescata dal callback del GPS (non un tap), quindi venivano scartati. L'annuncio "Navigazione avviata verso..." al click "Vai" non bastava a "sbloccare" il motore perché scatta nel callback ASINCRONO di `directionsService.route()`, non più nella stessa call stack del tap originale (stesso problema, un passo più indietro). Fix: `primeSpeech()` — un'utterance vuota chiamata SINCRONAMENTE all'inizio dei gestori click di `#mainBtn`/`#miniMainBtn` (`handleStartStopClick()`) e `#navGoBtn`, prima di qualunque `await`/callback — sblocca il motore vocale per il resto della sessione.
- **Barra navigatore centrale** (`.nav-topbar`, `#navTopbar`, sopra la mappa nella colonna centrale, sempre visibile, testo ingrandito in questo round — 18px testo istruzione, 26px chevron, contro i 14px/20px di prima, ancora giudicati poco leggibili in marcia): sostituisce i vecchi overlay flottanti "pannello prossima manovra" + chip distanza/ETA che stavano sopra la mappa. In un'unica riga mostra: un chevron di manovra (`#navTopbarChevron`, ▶/◀/▲, mappato da `MANEUVER_CHEVRON` in base a `step.maneuver`), il testo istruzione (`#navTopbarText`, con la distanza alla prossima manovra in grassetto quando c'è un percorso attivo, es. "Tra **250 m** · Gira a destra su Via Roma"), la distanza residua totale del percorso (`#navTopbarDist`) e l'ETA (`#navTopbarEta`) — tutti aggiornati ad ogni fix GPS da `updateNavProgress()`/`updateRouteInfo()` (somma locale degli step non ancora completati, nessuna chiamata API aggiuntiva, non tiene conto del traffico in tempo reale). Senza percorso impostato la barra è in stato inattivo (classe `.nav-topbar.idle`, testo attenuato) con "Nessun percorso impostato".
- **Pulsanti navigatore ingranditi** (`.btn-mini`, usato da Vai/Annulla percorso/Chiudi nel popover navigatore e da Reset max/CSV/Chiudi altrove): tap target da 38px a 50px di altezza, font da 10px a 13px — bump globale sulla classe condivisa, beneficia tutti i pulsanti `.btn-mini` dell'app, non solo quelli del navigatore.
- **Rotazione mappa in base al senso di marcia — valutata, NON implementata in questo round**: richiederebbe o (a) un hack CSS che ruota l'intero `#gmap` in base all'heading, con lo svantaggio di rendere illeggibili/capovolte le etichette delle strade e gli altri elementi della mappa, oppure (b) passare a **Google Maps vettoriale** (richiede un Map ID configurato in Google Cloud Console sul progetto dell'utente, che supporta `map.setHeading()` nativamente senza il problema delle etichette). La (b) è la soluzione corretta ma richiede un passaggio di configurazione lato utente (Cloud Console) che non può essere fatto da codice; non implementata per evitare una versione "a metà" con etichette illeggibili. Riprendere se l'utente configura un Map ID.
- **Navigazione indipendente dalla registrazione telemetria**: funziona sia con **Avvia** premuto che senza.
- **Versione precedente (superata)**: prima di Google Maps c'era una minimappa con traccia GPS auto-disegnata (nessuna dipendenza esterna, funzionava offline) e poi una mappa OSM via Leaflet con rotazione CSS heading-up. Entrambe sostituite per limiti funzionali (niente routing reale) o di conformità (rotazione + attribuzione). Se in futuro serve una modalità completamente offline, quell'approccio è il punto di partenza da recuperare (vedi cronologia se necessario, ma il codice attuale non lo contiene più).

### Layout a tre colonne

Il layout HUD è organizzato in tre colonne fisse-elastiche (`.layout`, `display:flex; flex-direction:row`):

- **Colonna sinistra** (`.col-side.left`, `#colSideLeft`, 145px fissi — ridotti da 168px in questo round, "più spazio alla mappa"): dall'**alto** (spostata qui in questo round, vedi "Mini-riga" sotto) la mini-riga (`.mini-row`, 3 pulsanti Avvio/Menù/Calibra), poi gli slot `#slotLeftTop` e `#slotLeftBottom` — di default contengono rispettivamente la card **Piega** e la card **Beccheggio**.
- **Colonna centrale** (`.col-center`, flessibile, `flex:1 1 auto`): la barra navigatore (`.nav-topbar`) sopra la mappa (`.col-map`/`#gmap`), che occupa tutto lo spazio verticale restante.
- **Colonna destra** (`.col-side.right`, `#colSideRight`, 145px fissi): un **unico slot a tutta altezza** (`#slotRight`, sostituisce i due slot `#slotRightTop`/`#slotRightBottom` + `.cockpit-void` di prima) che contiene di default la card **Trasferimento Carico** — scesa da 2 card (G Laterale/G Longitudinale) a 1 in questo round, vedi sezione "Card grandi". La vecchia `.cockpit-void` (spazio vuoto fisso, pensato per la porzione di schermo coperta dal quadro strumenti su alcune moto) è stata **rimossa**: lo spazio recuperato va al gauge Trasferimento Carico, più grande di conseguenza.
- **Landscape only**: invariato — se il telefono è in portrait, overlay "ruota il telefono" (`@media (orientation: portrait)`) al posto dell'interfaccia.

### Personalizzazione layout: scambio delle card grandi

- **Modalità modifica**: toggle "Modalità modifica" nel pannello comandi (`#editModeToggle`, Attiva/Disattiva). Quando attiva, aggiunge la classe `edit-mode` a `.app`, che rende visibili i pulsanti ⇄ (`.stat-swap-btn`, altrimenti `display:none`) su ciascuna delle card grandi. - **Scambio delle card grandi** (`cardLayout`, chiavi `leftTop`/`leftBottom`/`right` — **sceso da 4 a 3 slot/metriche in questo round**, vedi sezione "Card grandi"; valori `lean`/`pitch`/`load`): tap su ⇄ di una card apre un picker generico (`openPicker()`) con le altre metriche disponibili; scegliendone una, `swapCardInto()` **scambia le due posizioni** — è una permutazione stretta, ogni metrica occupa sempre esattamente uno slot, mai duplicata e mai assente. Lo scambio riappende gli elementi DOM reali nei nuovi slot (`applyCardLayout()`) e persiste in `localStorage` (`moto_card_layout`). `loadCardLayout()` valida il JSON salvato all'avvio: deve avere tutte le chiavi slot correnti, ciascuna con un metric-id valido, tutti distinti (`Set` di dimensione `SLOT_KEYS.length` — **generalizzato in questo round**, prima era un `4` fisso, così non si rompe se il numero di slot cambia ancora) — altrimenti il salvataggio viene ignorato e si usa il default (`leftTop: lean, leftBottom: pitch, right: load`).
- Nota: scambiando la card Trasferimento Carico (di default nello slot destro a piena altezza) con Piega/Beccheggio (slot sinistri, metà altezza) il gauge cambia proporzioni di conseguenza (CSS flessibile) — non testato a fondo su schermi molto piccoli, da verificare se usato.

### Layout / UX pensata per l'uso in marcia

- **Landscape only**: se il telefono è in portrait, viene mostrato un overlay "ruota il telefono" (`@media (orientation: portrait)`) invece dell'interfaccia.
- **Tutti i controlli raggruppati in alto** (questo round): la parte bassa dello schermo, una volta montato il telefono sul cupolino, si è rivelata scomoda da raggiungere in marcia — non solo per la mini-riga (vedi sopra, già affrontato nel round precedente) ma anche per il pulsante recenter mappa (spostato da in basso a destra a in alto a sinistra) e per l'apertura/chiusura dei popover (mitigata dai margini safe-area-aware, vedi sopra). Nessun controllo critico resta ancorato in basso.
- Font monospazio per i dati tecnici, Orbitron per i numeri "hero" (piega, beccheggio, G, punteggio) — tema "digitale/futuristico", griglia di sfondo sottile in stile blueprint. Sistema di **temi chiaro/scuro** (`:root[data-theme]`, token `--ink`/`--ink-dim`/`--hair`/`--bg`/`--bg2`/`--accent`): **notturno di default**, **diurno attivabile dal pannello comandi** (persistito in `localStorage`, vedi sopra). Trattamento diverso e più generoso per i popover, vedi sopra.

### Segnalino (nuovo in questo round)

Pulsante 🚩 (`#mapMarkerBtn`, in alto sulla mappa, visibile solo mentre si registra) per marcare al volo un istante/punto notevole durante la guida (es. "ho frenato troppo qui") senza dover interrompere la marcia per prendere appunti, poi ritrovabile e confrontabile nel CSV esportato.

- `addMarker()`: al tap, inserisce **subito** una riga dedicata in `logData` con uno snapshot completo dei valori correnti (timestamp `new Date()`, ultima posizione GPS nota, piega/beccheggio/G correnti) e `marker: 1` — non aspetta il prossimo fix GPS regolare (che nella pratica su strada arriva con ritardo variabile, fino a ~1s), per catturare l'istante esatto del tap.
- Le righe normali (da `handlePosition()`, un fix GPS) hanno `marker: ''` (vuoto); solo le righe da `addMarker()` hanno `marker: 1` — colonna aggiunta in fondo al CSV (vedi sezione Export).
- Nessun limite al numero di segnalini per sessione.

## Formato export CSV

Colonne, una riga per ogni fix GPS ricevuto durante una sessione di registrazione **più una riga per ogni segnalino** (vedi sezione "Segnalino"):
```
timestamp, lat, lon, speed_kmh, heading_deg, lean_deg, pitch_deg, accel_fwd_g, accel_lat_g, accel_vert_g, comfort_idx, score, marker
```
`accel_fwd_g`/`accel_lat_g`/`accel_vert_g` sono presi dall'ultimo campione `devicemotion` disponibile al momento del fix GPS (i due sensori non sono sincronizzati, GPS aggiorna a ~1Hz, motion molto più spesso — si prende sempre il valore più recente). Questo formato era rimasto un vincolo esplicito del piano di redesign layout v2 fino al round precedente (nessuna modifica alle colonne); **questo round ha aggiunto la colonna `marker`** in fondo (vuota `''` sulle righe normali, `1` sulle righe da segnalino) — prima estensione dello schema dal redesign v2, un tool esterno che leggesse solo le prime 12 colonne per posizione continua a funzionare, uno che leggesse per intestazione va aggiornato per la nuova colonna.

## Problemi noti / cose da verificare su strada

1. **Verso del beccheggio non validato** — vedi sopra, correzione di una riga se necessario in `computePitchFromGravity()`. La saturazione a ±90° (beccheggio che saliva poi tornava a scendere) è stata **corretta** — vedi sezione "Calcolo beccheggio" sopra — ma il solo *segno* (SU vs GIÙ) resta da confermare su strada.
1b. **Verso del TOP G laterale (DX/SX) non validato** — assume la stessa convenzione della piega perché condivide lo stesso asse compensato, ma non è la stessa misura fisica. Se risulta invertito, correzione di una riga in `updateGLatGauge()` (vedi sezione "G laterale/longitudinale" sopra).
1c. **Soglie deadzone ora calibrate dal vivo** (`G_DEADZONE`, `LEAN_DEADZONE_DEG`, `PITCH_DEADZONE_DEG`) — vedi sezione "Calibrazione": misurate a 3 deviazioni standard del rumore reale raccolto per ~1.5s ad ogni tap di Calibra, non più valori fissi. Restano comunque un'euristica non validata scientificamente (perché 3 deviazioni standard e non 2 o 4, perché 1.5s e non di più) — da aggiustare se in marcia risultano ancora troppo/poco aggressive.
2. **Apertura da webview integrata** — se l'app viene aperta tramite un link condiviso dentro un'app che usa una webview interna (non Safari "vero"), i permessi di sensori/posizione possono essere negati o limitati anche se il sito è servito in HTTPS. Va sempre aperta da Safari come sito a sé stante.
3. **Soglie del punteggio e dei colori warn/danger** (25°/40° piega, pesi 40/35/25 del punteggio) sono punti di partenza ragionevoli ma arbitrari, non calibrati su dati reali.
4. **Chiave Google Maps esposta lato client** — inevitabile per un'app client-side pura, ma **deve** avere la restrizione HTTP referrer impostata (vedi Setup), altrimenti chiunque trovi la chiave nel repo pubblico può usarla a proprie spese.
5. ~~Copertura del quadro strumenti (`.cockpit-void`)~~ — **non più applicabile**: rimossa in questo round insieme al vincolo "controlli non raggiungibili in basso" che rappresentava (tutti i controlli sono stati spostati in alto, invece di convivere con una zona morta in basso — vedi sezione Layout). Lo spazio è stato riassegnato al gauge Trasferimento Carico.
6. **Mappa offline**: con Google Maps, senza connessione dati la mappa non carica (tile scaricati al volo). Il resto dell'app (sensori, GPS, log, export) funziona comunque regolarmente.
7. **Nessun salvataggio persistente delle sessioni**: i dati registrati vivono solo in memoria (`logData` array) fino all'export CSV manuale — chiudere/ricaricare la pagina durante una registrazione perde tutto. Se serve resilienza (es. salvataggio incrementale), andrebbe aggiunto `localStorage`/IndexedDB.

Effetto solo visivo (i due campi tornano popolati con valori non significativi anziché restare vuoti), individuato durante la review del redesign layout v2 ma lasciato "parcheggiato" perché preesistente all'app originale e fuori scope per questo piano.
